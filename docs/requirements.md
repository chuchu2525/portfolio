# ポートフォリオサイト要件ドラフト

このドキュメントは `prototypes/v2` をベースに、最終版ポートフォリオサイトの要件を固めるための作業メモです。まだ確定仕様ではなく、今後の会話で更新していく前提です。

## 目的

エンジニアとしてのスキル、経験、思想が伝わるポートフォリオサイトを作る。

単なる職務経歴の羅列ではなく、ユーザー本人の興味である「古着」と「レコード」をデザインの中心に置き、技術的な整理力と個性が同時に伝わるサイトにする。

## 主な閲覧者

主対象:

- 転職・採用担当者
- エンジニア・開発者

副次対象:

- 仕事依頼や知人紹介経由の閲覧者

優先順位:

- まずは採用担当者とエンジニア向けに作る
- 仕事依頼向けの導線は最低限あればよく、現時点では深く考えすぎない

閲覧者ごとの見せ方:

- 採用担当者には、強い領域、できること、経験年数や経験量が短時間で伝わるようにする
- エンジニアには、技術選定、設計、実装判断、プロジェクトでの役割が分かるようにする
- Home はどちらの立場でも理解できる要約にする
- 技術的に細かい話はプロジェクト詳細ページで扱う

## 情報設計

現時点では以下のセクションを想定する。

### サイト構成

方針:

- ハイブリッド構成にする
- トップページに Home / Skills / 代表Projects / About / Contact をまとめて載せる
- プロジェクト詳細は必要に応じて個別ページを作る

理由:

- 初見の人にはトップページだけで世界観と主要情報が伝わる
- 詳しく見たい人にはプロジェクト詳細で深掘りできる
- 1ページ完結より情報を増やしやすく、完全な複数ページ構成より見てもらいやすい

未確定:

- トップページにどこまで詳しく載せるか
- プロジェクト詳細ページを何件分作るか
- Skills や About に個別ページを持たせるか

### Home

役割:

- 第一印象を作る
- エンジニアであることと、古着・レコードの世界観を同時に伝える
- Projects / About / Skills への導線を置く
- 採用担当者にもエンジニアにも、強い領域・できること・経験量が分かるようにする
- レコード盤のビジュアルで、各技術領域と強さを直感的に見せる

含めたい要素:

- 名前またはハンドル
- エンジニアとしての短い肩書き
- 一言のコンセプトコピー
- 強い領域
- できることの要約
- 経験年数または経験量の目安
- レコード盤とスキルレーダーのビジュアル
- レコード盤の周囲に、主要な技術領域名を表示する
- レーダーの形で「どの領域がどのくらい強いか」を見せる
- 主要CTA

Homeで伝える強みの仮方針:

- 複合型として見せる
- ただし、ぼやけないように主軸は「Webアプリ開発を一通り進められるフルスタック寄り」とする
- その中でも、UI実装・体験改善・プロダクト改善に強みがある見せ方にする

Home直下のコンテンツ候補:

- Recent Patches: 最近の更新、直近の取り組み、代表的な改善
- Featured Product / Project: 代表プロダクトや一番見せたい経験
- どちらにするかは未確定。v2 のように `Recent Patches` として置きつつ、内容はプロダクト/経験の紹介に寄せる案が有力

未確定:

- 表示名を本名、ハンドル、ブランド名のどれにするか
- Heroコピーを日本語中心にするか、英語見出しを残すか

### Recent Patches

役割:

- 直近または代表的な経験を2〜3件だけ先に見せる
- 「経験 = パッチ」「プロジェクト = 服に縫い付けるもの」という見立てを作る

含めたい要素:

- Featured な経験カード
- 小さめの補助カード
- 技術タグ
- Projects への導線

### Skills / Skill Matrix

役割:

- エンジニアリングの知識・経験を複数の属性に整理して視覚的に見せる
- レーダーチャートをレコード盤の中心要素として扱う
- 各属性をクリックすると詳細が切り替わる
- 属性数は5つに固定しない
- 属性は見た目の都合だけで決めず、できるだけMECEに近い整理にする

初期に検討していた属性:

- フロントエンド
- バックエンド
- DB
- インフラ
- CI/CD

確定方針:

- レーダーチャートは5角形に固定しない
- エンジニアリング全体をできるだけ漏れなく、重複少なく表せる分類にする
- 採用担当者にも分かり、エンジニアにも違和感が少ない粒度にする
- スコア配分は、項目が固まってから決める
- 技術レイヤー型をベースにしつつ、要件定義、アーキテクチャ、設計、品質、運用も表現できるようにする
- 要件設計とアーキテクチャ設計は別領域として扱う
- セキュリティとパフォーマンス改善は独立項目として扱う
- 各経験には複数の属性を付けられるようにする
- 経験ごとに「主属性」と「副属性」を持たせ、どの強みの話なのかを分かりやすくする
- レーダーのスコアは手入力の自己評価ではなく、登録した経験データから集計する
- レーダーの最大値は固定しすぎず、経験量に合わせて変更できるようにする

参考にした分類:

- SWEBOK V4.0: Software Requirements、Software Architecture、Software Design、Software Construction、Software Testing、Software Engineering Operations、Software Maintenance、Software Configuration Management、Software Quality、Software Security など
- SFIA: Requirements definition and management、Systems design、Software design、Programming/software development、Systems integration and build、Functional testing、Non-functional testing、Release management、Deployment、Application support など

確定する属性:

- 要件定義・課題整理
- アーキテクチャ設計
- フロントエンド
- バックエンド
- データ設計・モデリング
- 品質保証・テスト
- セキュリティ
- パフォーマンス改善
- インフラ・デリバリー
- 運用・改善

別枠で扱う可能性がある候補:

- プロダクト理解・業務理解
- UI/UX・体験設計
- 運用・信頼性

この案の意図:

- `要件定義・課題整理` は「何を作るべきか」を決める領域。課題ヒアリング、要求整理、仕様化、優先度付け、スコープ調整を扱う
- `アーキテクチャ設計` は「全体をどう作るか」を決める領域。システム分割、技術選定、非機能要件、拡張性、トレードオフ判断、AWSのサービスを組み合わせた冗長構成などを扱う
- `フロントエンド` はユーザーが直接触る画面を作る領域。UI実装、状態管理、フォーム、アクセシビリティ、レスポンシブ対応、体験品質を扱う
- `バックエンド` は画面の裏側で動く処理を作る領域。API、認証認可、業務ロジック、バッチ、外部サービス連携を扱う
- `データ設計・モデリング` はデータをどう持ち、どう取り出すかを設計する領域。DB設計、スキーマ、クエリ、インデックス、マイグレーションを扱う
- `品質保証・テスト` は壊れにくさと確認しやすさを作る領域。単体テスト、結合テスト、E2E、レビュー、テストしやすい設計、品質基準を扱う
- `セキュリティ` は安全に使える状態を作る領域。認証認可、権限設計、入力検証、秘密情報管理、脆弱性対策、セキュアコーディングを扱う
- `パフォーマンス改善` は速く、重くなりにくくする領域。フロント表示速度、APIレスポンス、DBクエリ、キャッシュ、負荷対策を扱う
- `インフラ・デリバリー` は作ったものを環境に載せて届ける領域。クラウド、CI/CD、デプロイ、環境構築、リリースフロー、監視基盤を扱う
- `運用・改善` はリリース後に育て続ける領域。障害対応、ログ確認、保守、問い合わせ対応、継続的改善、運用品質の向上を扱う

経験への属性付けの例:

- AWSでALB、ECS、RDS Multi-AZ、S3、CloudFrontを使って冗長構成を設計した経験は、主属性を `アーキテクチャ設計` とする
- 副属性として `インフラ・デリバリー`、`運用・改善`、`セキュリティ`、`パフォーマンス改善` を付けられるようにする

スコア集計ルール:

- 経験の各属性に `経験あり` または `キャッチアップ中` の状態を付ける
- `経験あり` は `1.0` として集計する
- `キャッチアップ中` は `0.5` として集計する
- 各属性の合計値をレーダーチャートに反映する
- レーダーチャートの最大値は設定で変更できるようにする
- 詳細表示では、単なる点数ではなく、どの経験がそのスコアに寄与しているか分かるようにする

懸念:

- 10項目になるため、レーダーが読みにくくならないようラベル配置と詳細表示を工夫する
- 重要度の低い項目まで並べると、何が強い人なのかがぼやける
- `プロダクト理解・業務理解` は採用担当者には伝わりやすいが、エンジニアリング知識のレーダーとしては別枠にする可能性がある
- `CI/CD` は単独項目から外し、インフラ・デリバリーに含める方が重複が少ない

現在の仮属性と服パーツの対応案:

- フロントエンド: 前身頃、見える面
- バックエンド: 裏地、見えない強度
- DB: ポケット、収納と取り出し
- インフラ: 裾、土台
- CI/CD: リベット、留め具

含めたい要素:

- レーダーチャート
- 属性タブ
- 属性ごとの説明
- スキル内訳のバー
- ケアラベル風の補助情報

未確定:

- 集計値を画面上に数値として出すか、レーダー形状と詳細説明だけで見せるか
- 属性名を画面上で日本語にするか、短い英語ラベルも併記するか
- `プロダクト理解・業務理解` や `UI/UX・体験設計` をレーダー外でどう見せるか

- 経験カードを追加する
- 経験に属性を付ける
- 属性名を変更する
- 属性スコアを変更する

本番での扱いは未確定。

案:

- 案A: 本番では編集機能を消し、静的なポートフォリオにする
- 案B: ローカルJSONやCMSからデータを管理し、サイト上には編集UIを出さない
- 案C: 管理者だけが使える編集UIを作る

現時点では案Bが現実的。見た目は編集可能なモックで検証し、最終的にはデータファイルから生成する構成に寄せる。

## 技術構成の候補

最終実装の候補:

- Astro
- Next.js
- Vite + React
- 静的HTML/CSS/JS

決定方針:

- ポートフォリオとしては静的生成で十分
- Next.js + React + TypeScript を採用する
- Next.js は App Router を使い、`output: "export"` で静的ファイルとして書き出せる構成にする
- データは TypeScript のデータファイルに寄せ、将来的に JSON/Markdown/CMS に移しやすい形にする
- インタラクションは軽めにする
- v2 の編集 UI は本番ページには出さず、登録済みデータから表示する
- レーダースコアは手入力ではなく、経験データの属性状態から集計する
- 画像最適化、OGP、メタ情報を Next.js 側で扱う

スタイリング方針:

- Tailwind CSS を採用する
- `app/globals.css` は Tailwind import、CSS変数、`html`、`body`、フォーム要素などの全体共通スタイルに限定する
- セクションやコンポーネント固有の見た目は、原則として React コンポーネント側の Tailwind utility class で表現する
- レコード盤、レーダー、縫い目、ラベルなどの複雑な装飾は、可読性を優先し、必要最小限の CSS class や inline style を併用してよい

## 非機能要件

- モバイルでも読みやすい
- テキストがカードやボタンからはみ出さない
- 装飾が情報理解を邪魔しない
- レコード盤などのアニメーションは `prefers-reduced-motion` に対応する
- Lighthouseで大きな問題が出ない程度のパフォーマンス
- OGP、favicon、メタ情報を用意する
