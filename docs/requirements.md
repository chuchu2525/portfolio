# ポートフォリオサイト要件

このドキュメントは、古着とレコードをモチーフにしたエンジニア向けポートフォリオサイトの要件を管理するための正本です。

デザイン参照は `prototypes/v2`、実装の主軸は Next.js / React / TypeScript 版とします。要件が会話で固まったら、まずこのファイルを更新してから実装へ反映します。

## 現在の決定事項

- 表示名 / ロゴは `YUU's room` にする
- 肩書きは `Full-stack Web Engineer` にする
- Hero見出しは `課題を解決する、利益をあげるエンジニア` にする
- トップページは Hero / Skill Matrix / Featured Projects / Profile / Contact の順に見せる
- Hero直下は代表実績ではなく Skill Matrix にする
- Skill Matrix はスコア評価表ではなく、経験の根拠へ入るナビゲーションUIとして扱う
- Projects はトップでは代表実績3件程度に絞り、全件一覧は `/projects`、詳細は `/projects/[id]` に分ける
- About は自己紹介単体ではなく、`Profile / Liner Notes` として役割と経歴の要約を置く
- Contact は GitHub / LinkedIn / Wantedly をまず置く
- 本番ページには v2 モックの編集UIを出さない

## 目的

エンジニアとしてのスキル、経験、思想が伝わるポートフォリオサイトを作る。

単なる職務経歴の羅列ではなく、ユーザー本人の興味である「古着」と「レコード」をデザインの中心に置き、技術的な整理力と個性が同時に伝わるサイトにする。

## 主な閲覧者

主対象:

- 転職・採用担当者
- エンジニア・開発者

副次対象:

- 仕事依頼や知人紹介経由の閲覧者

優先順位:

- まずは採用担当者とエンジニア向けに作る
- 仕事依頼向けの導線は最低限あればよく、現時点では深く考えすぎない

閲覧者ごとの見せ方:

- 採用担当者には、強い領域、できること、経験年数や経験量が短時間で伝わるようにする
- エンジニアには、技術選定、設計、実装判断、プロジェクトでの役割が分かるようにする
- Home はどちらの立場でも理解できる要約にする
- 技術的に細かい話はプロジェクト詳細ページで扱う

## 情報設計

現時点では以下のセクションを想定する。

### サイト構成

確定方針:

- ハイブリッド構成にする
- トップページに Hero / Skill Matrix / Featured Projects / Profile / Contact をまとめて載せる
- トップページは全情報を載せる場所ではなく、初見の閲覧者に「何ができる人か」「それを裏付ける経験があるか」「もっと見たいか」を判断してもらう場所にする
- 全実績一覧は `/projects` に分ける
- 代表実績や詳しく見せたい実績の詳細は `/projects/[id]` に分ける
- 詳細なプロフィールページは初期実装では必須にしない
- 本番ページには v2 モックの編集UIを出さない

理由:

- 初見の人にはトップページだけで世界観と主要情報が伝わる
- 詳しく見たい人にはプロジェクト詳細で深掘りできる
- 1ページ完結より情報を増やしやすく、完全な複数ページ構成より見てもらいやすい
- Skill Matrix と Projects の情報量が大きいため、トップページに全アーカイブや長い経歴を置きすぎない

トップページの順序:

1. Hero
2. Skill Matrix
3. Featured Projects
4. Profile / Liner Notes
5. Contact

初期実装の別ページ:

- `/projects`: 全実績一覧、属性・技術タグでの絞り込み、詳細ページへの入口
- `/projects/[id]`: 代表実績や詳しく見せたい実績の詳細

### Home

役割:

- 第一印象を作る
- エンジニアであることと、古着・レコードの世界観を同時に伝える
- Skill Matrix / Projects への導線を置く
- 採用担当者にもエンジニアにも、強い領域・できること・経験量が分かるようにする
- サイト全体の読み始めとして、誰のサイトか、何ができる人か、次に何を見るべきかを明確にする

確定する表示:

- ロゴ / サイト名: `YUU's room`
- 肩書き: `Full-stack Web Engineer`
- Hero見出し: `課題を解決する、利益をあげるエンジニア`

含める要素:

- 表示名またはサイト名
- エンジニアとしての短い肩書き
- 大きい見出し
- 強い領域
- できることの要約
- 経験年数または経験量の目安
- 主要CTA

Homeで伝える強み:

- 複合型として見せる
- ただし、ぼやけないように主軸は「Webアプリ開発を一通り進められるフルスタック寄り」とする
- その中でも、UI実装・体験改善・プロダクト改善に強みがある見せ方にする

UI/UX方針:

- Heroではコピーの細部を作り込みすぎず、サイト名、肩書き、見出し、導線を優先する
- Hero直下には Skill Matrix を置く
- レコード盤レーダーをHero内で過度に完結させず、次の Skill Matrix セクションへ自然に誘導する

### Recent Patches

このセクションは初期実装ではトップページの主軸にしない。代表実績は `Featured Projects` として扱う。

役割:

- 直近または代表的な経験を2〜3件だけ先に見せる
- 「経験 = パッチ」「プロジェクト = 服に縫い付けるもの」という見立てを作る

扱い:

- `Recent Patches` の表現は世界観として残してもよい
- ただしトップページの情報設計では `Featured Projects` を優先する
- 更新履歴としての Recent Patches は、必要になった段階で追加検討する

### Skills / Skill Matrix

役割:

- エンジニアリングの知識・経験を複数の属性に整理して視覚的に見せる
- レーダーチャートをレコード盤の中心要素として扱う
- 各属性をクリックすると詳細が切り替わる
- スコアを見せる評価表ではなく、経験の根拠へ入るナビゲーションUIとして扱う
- 属性数は5つに固定しない
- 属性は見た目の都合だけで決めず、できるだけMECEに近い整理にする

初期に検討していた属性:

- フロントエンド
- バックエンド
- DB
- インフラ
- CI/CD

確定方針:

- レーダーチャートは5角形に固定しない
- エンジニアリング全体をできるだけ漏れなく、重複少なく表せる分類にする
- 採用担当者にも分かり、エンジニアにも違和感が少ない粒度にする
- スコア配分は、経験データの属性状態から集計する
- 技術レイヤー型をベースにしつつ、要件定義、アーキテクチャ、設計、品質、運用も表現できるようにする
- 要件設計とアーキテクチャ設計は別領域として扱う
- セキュリティとパフォーマンス改善は独立項目として扱う
- 各経験には複数の属性を付けられるようにする
- 経験ごとに「主属性」と「副属性」を持たせ、どの強みの話なのかを分かりやすくする
- レーダーのスコアは手入力の自己評価ではなく、登録した経験データから集計する
- レーダーの最大値は固定しすぎず、経験量に合わせて変更できるようにする
- スコアの数字そのものは主役にしない
- 強みの根拠は、関連する経験やプロジェクトで示す
- 採用担当者には強みの概要が伝わり、エンジニアには経験の中身へ進める構成にする

参考にした分類:

- SWEBOK V4.0: Software Requirements、Software Architecture、Software Design、Software Construction、Software Testing、Software Engineering Operations、Software Maintenance、Software Configuration Management、Software Quality、Software Security など
- SFIA: Requirements definition and management、Systems design、Software design、Programming/software development、Systems integration and build、Functional testing、Non-functional testing、Release management、Deployment、Application support など

確定する属性:

- 要件定義・課題整理
- アーキテクチャ設計
- フロントエンド
- バックエンド
- データ設計・モデリング
- 品質保証・テスト
- セキュリティ
- パフォーマンス改善
- インフラ・デリバリー
- 運用・改善

別枠で扱う可能性がある候補:

- プロダクト理解・業務理解
- UI/UX・体験設計
- 運用・信頼性

この案の意図:

- `要件定義・課題整理` は「何を作るべきか」を決める領域。課題ヒアリング、要求整理、仕様化、優先度付け、スコープ調整を扱う
- `アーキテクチャ設計` は「全体をどう作るか」を決める領域。システム分割、技術選定、非機能要件、拡張性、トレードオフ判断、AWSのサービスを組み合わせた冗長構成などを扱う
- `フロントエンド` はユーザーが直接触る画面を作る領域。UI実装、状態管理、フォーム、アクセシビリティ、レスポンシブ対応、体験品質を扱う
- `バックエンド` は画面の裏側で動く処理を作る領域。API、認証認可、業務ロジック、バッチ、外部サービス連携を扱う
- `データ設計・モデリング` はデータをどう持ち、どう取り出すかを設計する領域。DB設計、スキーマ、クエリ、インデックス、マイグレーションを扱う
- `品質保証・テスト` は壊れにくさと確認しやすさを作る領域。単体テスト、結合テスト、E2E、レビュー、テストしやすい設計、品質基準を扱う
- `セキュリティ` は安全に使える状態を作る領域。認証認可、権限設計、入力検証、秘密情報管理、脆弱性対策、セキュアコーディングを扱う
- `パフォーマンス改善` は速く、重くなりにくくする領域。フロント表示速度、APIレスポンス、DBクエリ、キャッシュ、負荷対策を扱う
- `インフラ・デリバリー` は作ったものを環境に載せて届ける領域。クラウド、CI/CD、デプロイ、環境構築、リリースフロー、監視基盤を扱う
- `運用・改善` はリリース後に育て続ける領域。障害対応、ログ確認、保守、問い合わせ対応、継続的改善、運用品質の向上を扱う

経験への属性付けの例:

- AWSでALB、ECS、RDS Multi-AZ、S3、CloudFrontを使って冗長構成を設計した経験は、主属性を `アーキテクチャ設計` とする
- 副属性として `インフラ・デリバリー`、`運用・改善`、`セキュリティ`、`パフォーマンス改善` を付けられるようにする

スコア集計ルール:

- 経験の各属性に `経験あり` または `キャッチアップ中` の状態を付ける
- `経験あり` は `1.0` として集計する
- `キャッチアップ中` は `0.5` として集計する
- 各属性の合計値をレーダーチャートに反映する
- レーダーチャートの最大値は設定で変更できるようにする
- 詳細表示では、単なる点数ではなく、どの経験がそのスコアに寄与しているか分かるようにする

懸念:

- 10項目になるため、レーダーが読みにくくならないようラベル配置と詳細表示を工夫する
- 重要度の低い項目まで並べると、何が強い人なのかがぼやける
- `プロダクト理解・業務理解` は採用担当者には伝わりやすいが、エンジニアリング知識のレーダーとしては別枠にする可能性がある
- `CI/CD` は単独項目から外し、インフラ・デリバリーに含める方が重複が少ない

現在の属性と服・レコード要素の対応案:

- 要件定義・課題整理: Care label / 取扱表示
- アーキテクチャ設計: Pattern / 型紙
- フロントエンド: Jacket front / 見える面
- バックエンド: Lining / 裏地
- データ設計・モデリング: Pocket / 収納
- 品質保証・テスト: Stitch / 縫い目
- セキュリティ: Rivet / 留め具
- パフォーマンス改善: Groove / 溝
- インフラ・デリバリー: Hem / 裾
- 運用・改善: Repair tag / リペアタグ

含めたい要素:

- レーダーチャート
- 属性タブ
- 属性ごとの説明
- スキル内訳のバー
- ケアラベル風の補助情報
- 関連する経験カード
- `Projects` で詳しく見る導線

UI/UX方針:

- レコード盤の中に10項目レーダーを置く
- 周囲または近接エリアに短い属性ラベルを出す
- クリック / タップした属性の説明を右側、またはモバイルでは下に出す
- 説明パネルには「この属性の意味」「関連する経験」「使った技術」を出す
- スコア数値は控えめにし、経験の根拠を目立たせる
- 10項目レーダーが読みにくい画面幅では、リストやタブでの閲覧性を優先する

要検討:

- 属性名を画面上で日本語にするか、短い英語ラベルも併記するか
- `プロダクト理解・業務理解` や `UI/UX・体験設計` をレーダー外でどう見せるか
- スキル内訳バーの `level` を最終的に何として扱うか

## 編集機能について

v2 にはモックとして以下の編集機能がある。

- 経験カードを追加する
- 経験に属性を付ける
- 属性名を変更する
- 属性スコアを変更する

本番方針:

- 本番ページには編集UIを出さない
- 管理者向け編集UIも初期実装では作らない
- データは TypeScript のデータファイルから表示する
- 将来的に JSON / Markdown / CMS へ移せる形にする

理由:

- ポートフォリオとしては静的生成で十分
- 管理画面を作ると実装範囲が広がりすぎる
- スコアは経験データから集計するため、画面上で任意に変更できる必要がない

## データモデル

実装では `lib/portfolio-data.ts` を正とする。

### SkillAttribute

```ts
type SkillAttribute = {
  id: SkillAttributeId;
  label: string;
  displayName: string;
  shortName: string;
  garmentPart: string;
  description: string;
  stack: Array<{
    name: string;
    level: number;
  }>;
};
```

### Project

```ts
type ExperienceLevel = "experienced" | "learning";

type Project = {
  id: string;
  title: string;
  role: string;
  period: string;
  description: string;
  attributes: Array<{
    id: SkillAttributeId;
    level: ExperienceLevel;
  }>;
  techTags: string[];
  featured?: boolean;
  coverCode: string;
  highlights: string[];
};
```

データモデルの要検討:

- `Project` という名前で実績、経験、制作物をすべて扱うか
- 実務経験と個人制作を分けるか
- `links` を戻すか
- `problem`、`approach`、`result`、`learned` のような詳細項目を追加するか
- スキル内訳バーの `stack.level` が何を意味するか

## 技術構成

確定方針:

- ポートフォリオとしては静的生成で十分
- Next.js + React + TypeScript を採用する
- Next.js は App Router を使い、`output: "export"` で静的ファイルとして書き出せる構成にする
- データは TypeScript のデータファイルに寄せ、将来的に JSON/Markdown/CMS に移しやすい形にする
- インタラクションは軽めにする
- v2 の編集 UI は本番ページには出さず、登録済みデータから表示する
- レーダースコアは手入力ではなく、経験データの属性状態から集計する
- 画像最適化、OGP、メタ情報を Next.js 側で扱う

スタイリング方針:

- Tailwind CSS を採用する
- `app/globals.css` は Tailwind import、CSS変数、`html`、`body`、フォーム要素などの全体共通スタイルに限定する
- セクションやコンポーネント固有の見た目は、原則として React コンポーネント側の Tailwind utility class で表現する
- レコード盤、レーダー、縫い目、ラベルなどの複雑な装飾は、可読性を優先し、必要最小限の CSS class や inline style を併用してよい

## 非機能要件

- モバイルでも読みやすい
- テキストがカードやボタンからはみ出さない
- 装飾が情報理解を邪魔しない
- レコード盤などのアニメーションは `prefers-reduced-motion` に対応する
- Lighthouseで大きな問題が出ない程度のパフォーマンス
- OGP、favicon、メタ情報を用意する
- テスト方針と品質基準は `docs/test-design.md` を参照する
- アクセシビリティは、まず品質目標として `WCAG 2.2 AA 相当` を目指す。ただし正式な適合宣言ではなく、自動テストと手動確認を組み合わせて主要な問題を防ぐ
- ブラウザ確認は Chrome / Safari / Firefox、代表画面幅は mobile 390px / tablet 768px / desktop 1440px を標準にする
